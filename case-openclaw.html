CASE STUDY / OPENCLAW · 2026

One message in.
One production artifact out.

OpenClaw is a Telegram-native AI workflow running on a Linux VPS I provision and operate myself. An operator sends one structured message; the system routes it through an LLM, materializes the result as files on disk, renders a self-contained HTML board with a deterministic Python renderer, and publishes it as a static page. No dashboard, no forms, no frontend to babysit — chat is the whole control plane.

§02 / Design decisions

Why it's built this way.

  • Chat as the only control plane. A bot the operator already lives in beats a dashboard nobody opens. Every capability is reachable from a phone, and the interaction log doubles as an audit trail.
  • Artifacts are files, not rows. Intermediate state lives on disk as JSON + markdown: versionable with git, inspectable with cat, replayable through the renderer without re-paying the LLM. When a board looks wrong, the diff says whether the model or the renderer is to blame.
  • The model writes data; code writes HTML. Splitting generation (LLM → structured artifact) from presentation (deterministic render.py) means output quality is debuggable and the design system is enforced by code, not by prompt engineering.
  • Minimal public surface. The gateway binds to loopback; the public artifact is a static page. The attack surface of the serving path is a CDN's, not my VPS's.
  • Static output as an SLA. A self-contained HTML file has no cold starts, no runtime errors and no dependencies to patch. The boards below will render identically years from now.

Scope note: this page only claims what the public artifacts demonstrate. Server configuration details (hosting, exact hardening checklist, throughput) are available on request — I'd rather under-claim here than decorate.

§04 / Honest limits & next steps

What it is not, yet.

  • Single-tenant by design. It automates one operator's work. Multi-user would need real queueing, per-user workspaces and authorization — none of which I'll claim before building.
  • Not yet instrumented. I don't publish latency or throughput numbers because I haven't measured them rigorously; adding tracing around each stage is the next task.
  • Renderer templates are hand-grown. Extracting them into a documented theme system would make new board types a data change instead of a code change — the same lesson the 3D city's registry already applies.
