CASE STUDY / PORTFOLIO CITY · 2026

A city in
266 draw calls.

The 3D mode of this portfolio is a procedural isometric city — Tokyo Tower, Taipei 101 and six other landmarks, each hosting one real project, connected by drivable streets with traffic, pedestrians and a day/night cycle. It is 4,993 lines of vanilla ES modules with a single runtime dependency (three.js), and it is engineered to a measured frame budget instead of a vibe.

§01 / The problem

A portfolio that has to prove itself.

A 3D portfolio is a risky pitch: if it stutters on a recruiter's laptop, it argues against the engineer who built it. So the constraints were set up front:

  • No framework, no engine, one dependency. Everything above raw three.js — the world generator, vehicle controller, day/night system, HUD, minimap, audio — is written from scratch, so every line is defensible in a code review.
  • A hard frame budget. The whole island is procedural, so it is easy to accidentally emit thousands of meshes. Draw calls are measured, not guessed.
  • Runs on phones. A second render tier with different quality decisions, not just a smaller canvas.
  • Accessible, even though it's a game. Screen-reader announcements, keyboard-complete UI, WCAG AA contrast, and prefers-reduced-motion support.
  • No assets to download. Every building, vehicle, tree and sound is generated in code — the network payload is the code itself plus fonts and UI screenshots.
§02 / Architecture

One data file drives everything.

projects.data.js is the single source of truth: each entry declares its landmark builder, world position, proximity radius, accent color and card copy. The world generator, HUD cards, minimap dots, visit tracker and guide arrow all derive from it — adding a project is one data entry plus one procedural builder function.

The runtime is ~38 small modules in plain ES: core/ (renderer tiers, camera rig, post pipeline, day/night, synth audio), world/factory/ (procedural builders for landmarks, buildings, traffic, trees), vehicle/ (arcade controller with per-vehicle handling presets — a kart and a YouBike share one controller), ui/ (DOM overlay: HUD, minimap, dialogs) and projects/ (proximity system with enter/exit hysteresis and neighbor hand-off).

§03 / The draw-call budget

Merging until the GPU stops caring.

Procedural generation loves to emit one mesh per part — a market stall is a counter, a roof, four posts, an awning and a sign. Multiplied across a city, that becomes hundreds of draws with hundreds of unique materials, and every draw is paid up to three times per frame (shadow pass, AO pre-pass, main pass). The fix is boring and effective: pool materials at module scope so identical colors share one instance, then bake vertex colors and merge geometry per material bucket — with a custom mergeStatic() that skips anything live (emissive day/night materials, instanced meshes, textured signs).

Just as important: what was not merged. Anything that animates (lantern strings bob per string), glows on a day/night schedule (emissive materials are lerped by one system scanning userData.nightE tags), or carries a canvas texture stays live. The merge utility filters these automatically, so builders stay readable and the optimization is opt-out, not hand-maintained.

§04 / Post pipeline & adaptive quality

Paying for pretty, but with a cap.

The high tier renders through an EffectComposer chain: scene → ground-truth ambient occlusion (GTAO) → bloom → color grade + vignette → tone-map. Two decisions keep it honest:

  • The post pipeline is capped at 1.5× device-pixel-ratio (Post.MAX_DPR). GTAO and a bloom mip-chain at native 2× DPR is the single largest GPU cost on a laptop, and through bloom + grade the difference is invisible. ~44% fewer shaded pixels at DPR 2.
  • Adaptive quality degrades in the right order and stays degraded. A frame-time EMA first sheds the AO pass (>26 ms), then lowers a persistent DPR ceiling to 1.25 (>33 ms). The ceiling matters: a naive setPixelRatio call is silently reverted by the next resize event — which on phones fires on every URL-bar show/hide, exactly on the devices that needed the downgrade.

War story: screen-space AO hated the sky. The sky dome and cloud sprites have no usable depth/normals and produced black smears in the AO pass. Fix: atmosphere lives on layer 1, and the GTAO pass renders through a layer-0-only clone camera that stays in lock-step with the follow camera — the sky is composited but never occluded.

The hot loop is allocation-free: pedestrian path closures write into a shared scratch object, the ring-road parametric writes into a caller-provided struct, and the HUD caches its DOM measurements so proximity tooltips never force a synchronous reflow. Under prefers-reduced-motion the ambient animation clock freezes and the world update early-returns when its inputs are unchanged — zero recompute, zero instance-buffer uploads.

§06 / Accessibility for a game UI

Drivable with a screen reader running.

  • Game state is announced through a polite live region: approaching a landmark, opening a project card, switching vehicle or day/night, visit progress ("Discovered Milingua at Raohe Night Market — 5 of 8").
  • The whole flow is keyboard-complete: WASD/arrows drive, T/E/Enter opens the project at a landmark, the revealed card receives focus so Enter opens the project link, Escape dismisses. The intro is a real dialog: focus trap, Escape, focus restore.
  • Reduced motion is honored end-to-end: traffic, pedestrians, clouds, beacons, the guide arrow and every CSS animation freeze; driving stays user-controlled.
  • Contrast is tokenized: the accent color that fails WCAG AA as text (3.0:1) has a dedicated deep variant (≥4.8:1) used for every chip and label; hit targets meet the 24px minimum.
  • No-WebGL and no-JS fallbacks route to the classic page; the SEO content behind the canvas is a real focusable document, revealed as a panel when keyboard focus enters it.
§07 / Verify it yourself

Numbers you can reproduce in the console.

Open the live city, then in DevTools:

const { engine, camera } = window.__city
const info = engine.renderer.info
info.autoReset = false; info.reset()
engine.render(camera.cam)          // one isolated scene pass
console.log(info.render.calls, info.render.triangles)
info.autoReset = true

Deterministic camera setups for screenshots and QA are URL-addressable: ?shot (overview), ?shot=night, ?shot=play (gameplay framing), ?shot=lm:<projectId>,night (any landmark). Every figure on this page was captured through those URLs.

§08 / Honest next steps

What I'd do with another week.

  • Merge the remaining live emissive meshes per color bucket (window strips share one material but still cost one draw each).
  • Move pedestrian/traffic animation into a vertex shader or GPU instancing attributes to drop the per-frame matrix uploads.
  • Bake a light probe for night emissive bounce instead of leaning on bloom.
  • Measure and publish frame times per GPU class — draw calls are architecture, milliseconds are the product.
